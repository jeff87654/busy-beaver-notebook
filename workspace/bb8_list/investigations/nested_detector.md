## 1. How the f_{omega+1} champions work
The wiki has no analyses of these machines (their pages link only to Discord), so everything below comes from literal
simulation (`tview.exe`: run-length views at tape-end events, with an optional constructed start tape) and from
dlscan3's probes. Notation: tape words are read from the far end towards the head, and the head is on the blank
cell right after the word. `1^k` is a run, and `(110)^n` is a repeated block. The L-side machines are written
mirrored, as dlscan does.

All four champions have the same engine: an Ackermann (f_omega) digit list K(ds; a; b) to the right of an outer
part P. They differ in what P holds and in what happens when the list is used up.

**BB(13)** `1RB1RA_1LC1RD_1LA1LC_1LG0RE_1LC1RB_0RL1LG_0LM0RH_1RI1RH_1LK0RI_---0LK_1LF1LK_1LJ1RL_1RZ1RH`
- Steps 0 to 1.18e7 are a Collatz-like preamble on 1^n: n becomes about 5n/3 per pass (7, 16, 31, 56, 97, ..., 3682,
  6141), going through (110)^(n/3). It stops at the first n divisible by 3, 6141 = 3*2047.
- At step 11,798,795 the tape is (110)^2047 11. From then on the right-end configurations (state L) are
  `(110)^n 1 0 [digits 1^(2d) separated by 0] 1^b`, an Ackermann list: the last digit drops by 1 and
  b -> 2b+6, and a digit that reaches 0 borrows from the left and is refilled from b. For example, step 1.18e7
  shows `(11 0)x2046 1 0 11 00 1^22 0 1^58`, and step 5.7e9 shows `... 1 00 1^131064 0 1^24 0 1^26`.
- Used-up inner list: `(110)^3 1 0 1^10` becomes `(110)^2 1 0 111 (0 11)^8 0 1^10` in 613 steps. One 110 is
  consumed and a new list of about b digits is built.
- The counter is empty: `1 0 1^b` halts in 14 steps.
- dlscan3's chain from the census configuration, with the counter shrunk to 6, 12 and 18 periods, gives exactly
  6, 12 and 18 rebuilds and then a halt, for every test b. So the n = 2046 counter gives about 2046 nested f_omega
  applications: f_{omega+1}(2046).
- Caveat: the leading inner digit's parity matters. `(110)^n 0 1 0 1^b` halts whatever n is. The chain follows the
  census configuration's parities, not a proof of the real ones.

**BB(14)** `0LH0LL_1RI1RC_0LD1LG_0RE1LD_---1RF_---0RM_1RM0LH_1LG1LH_0LN0RJ_1RZ0LK_0LK1LL_1LG1LA_1RB1RM_0LG1LN`
(mirrored)
- Configuration: `1^(2n+r) 00 1 0 [digits 1^(d+1) separated by 0] 1^b`, with R1 b -> 3b+1.
- Used-up list: `1^10 00 1 0 1^13` becomes `1^8 00 11 (0 1)^6 0 1^4` at step 298 of the real run. The counter
  loses 2 cells and a list of about b/2 digits is built.
- At n = 0, `1 00 1 0 1^b` (r = 1) halts in about 35 steps.
- `1 0 1^b` (r = 0) creates a new counter `1^(b-2) 00`. Whether that round ends in a halt then depends on b's
  parity. The run starts with the counter 1^12 built at step 109.
- So this is f_{omega+1} with parity control: f_{omega+1}(f_omega^4(f_7(3))) on the wiki.

**BB(15)** `1LN1RI_1RA0RC_1RB1LD_0LD1LE_1LF1RG_1RH0LE_0RE1LD_1RB1RH_1RZ0RJ_1LN0LK_0LK1LL_1LM1LM_1RH0LL_1LO1LN_0LH1LN`
(mirrored)
- The census sees a plain list with a 2-cell prefix: `1 0 11 0 1^117 0 1^89 0 1^97`.
- Used-up list: `1 0 1 0 1^b` becomes `1^(b+6) 00 1 0 1^4` and then `1^(b+3) 00 [small list]`. The accumulator
  becomes a BB(14)-style counter, which later rebuilds consume (3 cells each in the chains).
- **Why dlscan2 "recognised" BB(15):** its list is visible with a prefix of at most 4 cells, so R1-R3 fit (template
  L,F,P=10,u=1,s=10). R4 then timed out, because the used-up list grows the counter prefix 1^(b+3) 00, which
  dlscan2's exact-prefix parse rejects. The grade was NOBOUNDARY, with no sign of the nesting.

**BB(16)** `1RB1RA_1RH0RC_1RB1LD_0LD1LE_1LF1RG_1RA0LE_0RE1LD_1LO1RI_1RZ1RJ_0LO0RK_1LO0LL_0LL1LM_1RA1LN_0LM0LM_1LP1LO_0LA1LO`
(mirrored)
- Configuration: `1^(4n+r) 00 1 0 1 0 [list] 1^b`.
- Used-up list: `1^8 00 1 0 1 0 1^9` becomes `1^4 00 1 0 111 (0 1)^8`. The counter loses 4 cells.
- `11 00 1 0 1 0 1^9` re-creates the counter as `1^15 00 ...`, and `1 00 1 0 1 0 1^9` halts.
- So this is BB(14)'s scheme with mod-4 control. Both counter creation and consumption show up in the chains.

**Why dlscan2 missed BB(13), BB(14) and BB(16):**
- The outer counter makes the far-end prefix longer than dlscan2's 4 cells (BB(14) and BB(16): 1^8 00).
- The BB(13) counter is 6,000 cells long, beyond the 4000-cell snapshot limit.
- BB(13)'s nested phase starts only after 1.18e7 steps. At census 1e6, BB(13) shows only the preamble.

## 2. The detector: dlscan3
Usage, the same as dlscan2's:
`nested_detector/dlscan3.exe MACHINES.txt OUT.tsv CENSUS PROBE [--all] [--span=32768] [--chainN=1000000] [--cap=40000000]`
- We use CENSUS = 1000000 and PROBE = 20000. CENSUS = 20000000 is needed for BB(13)-like late starts.
- `--tmpl MACHINE O Q P u s al be alB beB S [N]` runs the outer analysis of one hand-written template, with chain
  traces on stderr.
- `scan.py OUTDIR NPROC CENSUS FILES... [--exe dlscan3.exe]` runs parallel Idle chunked scans, resumable, with
  claim files.

Pipeline:
1. **Census:** dlscan2's census at both tape ends. Snapshots may be up to 32768 cells long (dlscan2: 4000). Besides
   the 12 commonest end kinds, the 6 kinds with the most recent snapshots are kept, so that a late phase is not
   crowded out.
2. **Templates:** dlscan2's templates (a memoised reimplementation, checked to give identical lists) plus
   **long-prefix templates**. The list is parsed from the head end for as long as its runs decode under one of
   the inferred encodings, and the rest of the snapshot, of any length, becomes the template prefix P.
   At most 2 groups per state are kept.
3. **R1-R3:** dlscan2's fit2, unchanged, run with that P.
4. **Outer analysis** of each fitted template (at most 6, long prefixes first):
   - Exhaustion probe: E(P; k; b) = P + k zero digits + a = 0 + accumulator b. The probe runs until a stable family
     configuration: two consecutive end configurations with the same outer part P' and the same number of digits,
     and b increasing. P' is whatever lies left of the decodable list.
   - A probe pair with b and b+1 classifies the step:
     - **R** rebuild: same P', more digits for b+1.
     - **C** counter creation: P' longer for b+1.
     - **F** refill: same P', same count.
     - **H** halt.
     - **T** no stable configuration within 1e6 steps.
     - **r** only b+1 halts.
     - **X** anything else.
   - A **chain** repeats this from the configuration each step leaves: P', with all of its digits zeroed. It runs
     for b1 = 2, 3, 4, 5 and up to 40 steps. It ends at H or T, or at a loop L: an outer state repeats, 3 rebuilds
     leave P unchanged, or the sequence of (P', step) becomes periodic.
   - A periodic block of P with more than 12 periods is shrunk to 6..11 periods, keeping the residue mod 6.
   - **Leading-digit chains** keep the list's first digit as a possible counter, starting at 2.
   - **z chains** start from k = n zero digits, where n is the digit count of the family's latest census snapshot.
     A real exhaustion is K(0^n; 0; b), and the zeros can matter.
5. **Checks against chain artefacts.** A chain uses a constant small b, and its used-up configurations are
   constructed, not observed.
   - **b > k confirmation:** a halting chain counts only if its halting exhaustion also halts with b = k+1..k+4. In a
     real run b is far larger than the list it has just cleared. The 76450 family, proved non-halting, "halts" only
     at exactly 4b+1 zeros.
   - **z requirement:** when the census list had digits, MULTI also needs a z chain that halts after a rebuild.
   - **Anchoring:** some snapshot of the template's state and prefix, taken in the later half of the family's life,
     must have digits that decode all the way to P. The accumulator and a may use another encoding: the BB(7)
     family writes a as (01)^(3a) and digits as (01)^(3d+1). Otherwise the template is "unanchored", and W1-HALTER
     and MULTI drop to W1-HALT? and MULTI?. In c35m14, a P=11, 2d+1 reading of the BB(8) record's list fits R1-R3 on
     constructed configurations, but its used-up form never occurs in the real run; it produced 145 false MULTI
     rows.
   - **Leading-digit chains** count for the counter test only. MULTI needs a base or z chain that halts after a
     rebuild.
   - **early** marks a family whose last census event came before half the census (a phase the machine left).
6. **Grades**, best first:
   - **W1-HALTER:** a chain halts after at least 1 rebuild (confirmed with b > k, anchored template), and the number
     of rebuilds before the halt grows strictly over three variants of an identified counter. The counter can be
     the periodic block of P (+6 and +12 periods), a counter created at C steps (b at the C steps +6 and +12), or
     the leading digit (2, 8, 14). A variant still rebuilding at its step limit counts with its lower bound.
   - **W1-HALT?:** the same, but unconfirmed or unanchored.
   - **W1-LOOPER:** a created counter is consumed by at least 2 rebuilds, and no chain halts.
   - **MULTI k:** a confirmed, anchored chain halts after k rebuilds, and k does not follow any counter: the
     f_omega^(k+1) shape. The k is that of a constant-b chain, so it is only indicative.
   - **MULTI?:** the same, unconfirmed or unanchored.
   - **LOOPER:** a chain loops with rebuilds; the list is cleared and rebuilt forever.
   - **REBUILD:** some step rebuilds, with no conclusion.
   - Otherwise the machine keeps its dlscan2 grade.
   - Only an identified counter can make a W1 grade. Without that rule, the BB(12) champion, whose rebuild count in
     constant-b chains drifts upward with b, was a false W1-HALTER.
- **Versions:** the 10-state scan chunks were run with the versions current at the time (v1 to v7: the same census
  and templates, with outer-analysis refinements).
  - c35m14 and the first 36 rec14 chunks were re-graded with v6 (`regrade.py`, in `scans/*/regraded.tsv`).
  - Every row graded W1-* or MULTI* anywhere was re-graded with the final v7 (`scans/w1multi_v7.tsv`).
  - v7 differs from v6 only in when W1 and MULTI apply. It changes no other grade, and machines without a fit are
    unaffected.

### Drivers and commands (for local jobs, no agent needed)
- **10-state subtrees.** `bash nested_detector/scans/run10c.sh [NPROC]` runs `scan.py` per source (rec14_0RH,
  rec14_1RE, rec14, r10m14, r10m13) with NPROC Idle workers and census 1e6.
  - It is resumable: finished chunks are skipped, and `--reset-claims` frees the claims of killed runs.
  - Run only one driver at a time.
  - A source's chunk list is fixed when it is first written. For machines appended later (subtrees still
    enumerating), scan into a new directory, e.g. `python scan.py scans/r10m13_b 2 1000000 FILES`, or delete
    `scans/NAME/chunks` and `scans/NAME/out` to rescan everything.
  - Re-grade fitted rows with `python regrade.py scans/NAME 2`.
- **BB(8) holdouts.** `python nested_detector/bb8_scan.py --workers 2 [--census 20000000] [--max-files N]` scans
  `jobs8/*/results/*_holdouts.txt` chunks that are not yet done, incrementally, like `neighbors/dlscan2_all.py`.
  - It writes `jobs8/<job>/dlscan3/<chunk>.tsv`, appends W1-*/MULTI rows to `nested_detector/dl3_hits.tsv`, and
    keeps `bb8_scan.lock`.
  - `--status` prints the totals. It is safe to stop and restart.
- **Which census.** 1e6 catches every structure that is already visible at 1e6: all of BB(14)-BB(16), the rec14
  loopers and the 0LJ0LC lead. A nested phase that starts late needs a longer census: BB(13)'s starts at step 1.18e7,
  so use >= 1.2e7, e.g. 2e7.
- **Cost trade-off.** Census 2e7 costs about 1.5-2x census 1e6 per machine (1.4 s vs 0.78 s per machine under load):
  the census itself grows 20x, the rest grows less. On 300 random rec14 holdouts, 2e7 found nothing that 1e6 missed
  (158 overlap with finished 1e6 chunks, identical grades). Recommendation: 1e6 for routine scans, and 2e7 for the
  machines that 1e6 grades NOBOUNDARY/REBUILD or for small high-value sets.

## 5. Cost
Measured per machine; the scans shared a fully loaded 16-thread PC with other Idle jobs, so treat these as upper bounds.
- **Without contention:** census 1e6, 50 rec14 holdouts at the start of the session: 0.27-0.33 s/machine. dlscan2 took
  0.1 s on the same machines.
- **In the scan:** 75k 10-state machines in 50 chunks took 0.78 s/machine of wall time per worker. The stages were the
  census (6%), template inference (57%), R1-R3 fits (31%) and outer analysis (6%). Machines with fits spend up to the
  outer-analysis cap of 4e7 probe steps, about 1-3 s.
- **Census 2e7:** 1.4 s/machine (300 rec14 holdouts), with the census itself 0.8 s.
- **BB(8) holdouts:** 3000-machine sample at 1.0 s/machine under load (templates 0.54 s, fits 0.44 s, no outer
  analysis because nothing fitted). A full scan of all 1,548,721 BB(8) holdouts (`jobs8/*/results/*_holdouts.txt`)
  would take about 1.55M x 0.4-1.0 s = 170-430 CPU-hours, roughly 1.5-3 days on 6 Idle cores. Its expected yield is
  very low:
  - the sample gave 0 R1-R3 fits in 3000 machines;
  - dlscan2 found list structure in only 27 of the 1.55M;
  - those 21 distinct machines, re-run here, gave no W1 grade and 3 MULTI?, all in the 76450 family, which is proved
    non-halting.
  A cheaper option, if wanted: run only the long-prefix template stage plus fits (dlscan2's own templates were
  already covered by its scans). That is about half the cost.
- **Token cost of this investigation:** about 820k tokens.

## 6. Limits
- The chains use a constant small b at every exhaustion. The real accumulators are huge, with "random" residues, so
  chains can follow paths the machine never takes. W1 grades rest on counter growth, which is robust to this; MULTI
  k values and halting parities are only indicative.
- Census length: a nested phase that starts after the census, like BB(13)'s at 1.18e7, is invisible. Scans at 1e6
  miss such machines.
- The outer counter must sit in the far-end prefix, be created from b, or be the list's first digit. A counter coded
  as digits inside the list (an alpha=1, beta=0 encoding that swallows it) is not separated.
- Evidence only: the probes construct configurations. A W1-HALTER hit needs an investigation and a proof.
