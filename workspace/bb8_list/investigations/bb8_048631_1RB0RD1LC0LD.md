# BB(8) holdout 48631: `1RB0RD_1LC0LD_1LA1RC_0LB0RE_1LF1RA_1LG---_0LH1LE_0LA0LB`

Source: holdout of BB(8) subtask 48631 (mxdys enumerator @ a41db6c). The undefined (halting) transition is F1.
Pipeline growth: 2 / 10 / 40 CPU-s gave 10,695 / 27,915 / 49,084 digits at 8,728 / 9,129 / 9,622 loops.

## Verdict

**The machine never halts.** It is a three-digit counter with tetration-rate growth. It never gets near the
record range and has no score.

**Confidence: proved (Coq PASS).** `bb8_list/proofs/BB8_48631_1RB0RD.v` proves `Theorem nonhalt : ~ halts tm c0.`
and passes `python check.py BB8_48631_1RB0RD.v`: the table matches the machine string, and `Print Assumptions`
reports "Closed under the global context". It compiles in about 220 s.

**D0 variants** (only D0 changed):
- `1RG0RE`: **same verdict, proved** (`BB8_48631_1RB0RD_D0_1RG.v`, PASS, ~220 s). In every context where D0
  fires, the next cell is 0, so `1RG` then `G0: 0LH` then `H1: 0LB` restores the original's effect two steps
  later. The macro-level behavior and every rule below are identical.
- `0RH0RE` and `1RB0RE`: **same verdict, proved** (`BB8_48631_1RB0RD_D0_0RH.v`, `BB8_48631_1RB0RD_D0_1RB.v`,
  both PASS, ~21 s each). Here D0 matters: the counter has two digits instead of three. Both variants follow
  the same rules; only their step counts differ.
  - **Families:** with the head in state E at the right end as above:
    - U1(z,x) = `(100)^z 00 (100)^x E> 100110`;
    - U2(z,x) = `(100)^z 01 (100)^x E> 100110`.
  - **Rules (x >= 5):**
    - U1(z+1,x) -->+ U2(z,3x+3);
    - U2(z+3,x) -->+ U1(z+1,3x+8);
    - reset U2(2,x) -->+ U2(3x+8,5): the outer digit is exhausted and x becomes the new outer digit.
  - **Why it never halts:** U2 always has z ≡ 2 (mod 3), because 3x+8 ≡ 2. So a phase always ends at U2(2,·), and
    the other endings never occur.
    - The blank tape reaches U2(224,5) after the first reset.
    - Coq indexes the counter as D(k,x) = U2(3k+2, x+5), with D(k+1,x) -->+ D(k,9x+67) and D(0,x) -->+ D(x+7,0).
    - It then applies `progress_nonhalt_simple`; no inequality is needed.
  - **Macro-simulator check:** the macro simulator (`vq.py`, 3-block alignment) sees the same counter as
    Q1(z,x) = `(100)^z 001 (100)^x`, Q2 = `...011...`. These are mid-bounce points of the same loops; the planner
    stops only at TL ends, which is why it uses U1/U2. There it confirmed Q1(z+2,x) -> Q2(z+1,3x+5),
    Q2(z+3,x) -> Q1(z+1,3x+10) and Q1(0,X) -> Q1(X-1,22) for x = 22..25, 70..73 and 100..102.

## The counter

All configurations below have the head in state E at the right end of the tape. The tape reads `... E> 100110`
followed by blanks. Blocks are written left to right, and the head reads the `1` right after the last written block.

```
PA(z,y,x) = 0^inf (001)^z 000 011 110 (010)^y 000 111 (001)^x 000 011 111^3 001 100  E> 100 110
PB(z,y,x) = 0^inf (100)^z 001 111 (001)^y 000 011 (001)^x 000 011 111^14 001 100      E> 100 110
PC(z,y,x) = 0^inf (010)^z 000 111 (100)^y (001)^x 000 011 111^47 001 100              E> 100 110
```

(These are string forms. The Coq families `PA`, `PB`, `PC` are the same strings written with the run
alignment that the planner produces.)

- z is the outer digit, y the middle digit and x the inner digit.
- The basic mechanism is the **tripling loop TL**: `X 111^b 100^c E> 100110` becomes `X 111^(b-1) 100^(c+3) E> 100110`
  after one bounce. So a run of b blocks `111` becomes 3b blocks `100`.
- One round runs TL a few times on the x digit. It multiplies x by 27, eats about 7 blocks of y, and eats one
  block of z. The phase of the tape rotates A -> B -> C -> A.

### Rules (all proved in Coq; the side conditions are the ones used in the proof)

| rule | statement |
|---|---|
| RA | PA(z+1, y, x) -->+ PB(z, y-7, 27x+3921)  (y >= 12, x >= 6) |
| RB | PB(z+1, y, x) -->+ PC(z, y-6, 27x+3974)  (y >= 12, x >= 6) |
| RC | PC(z+1, y, x) -->+ PA(z, y-8, 27x+4004)  (y >= 12, x >= 6) |
| EA | PA(0, y, x) -->+ PB(y-7, 27x+3918, 141)  (y >= 20, x >= 6) |
| EB | PB(0, y, x) -->+ PC(y-7, 27x+3973, 140)  (y >= 20, x >= 6) |
| EC | PC(0, y, x) -->+ PA(y-8, 27x+3999, 143)  (y >= 20, x >= 6) |
| Y4 | PA(z+5, 4, x) -->+ PC(z+1, 27x+3922, 140)  (x >= 6; the y digit runs out, used once) |
| INIT | blank -->* PA(216, 214, 143)  (step 431,579) |

- **Ending (z = 0):** the middle digit becomes the new outer digit, the old inner digit (tripled) becomes the new
  middle digit, and the inner digit restarts at 140-143.
- **Checks before the proof:** every rule was checked with an exact block-macro simulator (`msim.py`, no rule
  acceleration) on 660 parameter sets:
  - x in 4..15 and 50..52;
  - y in 8..23;
  - z in 0..2.
  All matched exactly (`verify_rules.py`). Earlier, the accelerated simulator (`fam.py`, `end1.py`, `end2.py`,
  `yend.py`) located the rules and their halting exceptions.
- **Where the machine could halt:** only near the ends of the digit ranges.
  - x digit too small: PA with x = 3, PB with x = 1 and PC with x = 0 halt.
  - y digit runs out: PA with y = 5, PB with y = 5 and PC with y = 6 halt.
  - Other small y give various endings.
  - The invariant below keeps the machine away from all of these.

### Trajectory and invariant

- **Initial part:**
  - blank -> PA(216, 214, 143);
  - then 30 rounds -> PA(186, 4, X) with X = G^10(143) = 2565014216298392717162929543872372061740642611, where
    G(x) = 27(27(27x+3921)+3974)+4004;
  - then Y4 -> PC(182, Y, 140) with Y = 27X + 3922 ≈ 6.93·10^46.
- **Second phase:** 182 rounds -> PB(0, ...) -> EB -> PC(z3, y3, 140) with z3 = 69255383840056603363399097684554045666997353137
  and y3 ≈ 10^264.4. Quick_Sim's run stops at the start of this third phase: its level-2 rule decrements the
  z3 digit (`010^69255383...353137`) by 30 per loop, so it would need about 2·10^45 loops to finish the phase.
- **Invariant** (Coq `Inv`), with w = y - 7z (minus 1 in phase C):
  - w >= 20 and x >= 6;
  - 8w <= 27^(z+1) x;
  - 27^z (x+155) <= 17·27^(w-7).
- **Why it holds:**
  - Rounds keep w fixed. Both bounds survive because x -> 27x + c with c <= 4030 = 26·155.
  - An ending uses both bounds. The lower bound gives new w >= old w + 3967. The upper bound gives the new first
    bound.
  - So once past the first phase, y never runs out before z does.
  - The start PC(182, Y, 140) satisfies the invariant, since Y ≈ 27^31 while 27^183 is huge.
- **Growth:** each phase exponentiates. The next inner digit is about 27^z times the current value, so the tape
  grows like 27↑↑n in the number of phases. The machine never halts, so the BB(8) record 2↑¹¹2↑¹¹3 does not
  apply.

## Formal proof (`bb8_list/proofs/BB8_48631_1RB0RD.v`)

**Generation:** `gen_coq.py` generates the file with a new planner, `planner9.py`, derived from
`neighbors_family_tools/planner8.py`. The planner mirrors busycoq's stepping on symbolic tapes.

**Run counts are affine forms** (`27 * x + kN 4083`) in a syntax that `simpl` never changes:
- `Nat.mul` is `simpl never`.
- Constants above 30 are `kN k`, with k an `N` numeral behind an opaque identity. This matters because unary
  numerals such as 4083 made each step 20x slower.
- Pure constants are always `kN k`.
- The planner emits every peel (`lpow_peel_gen`), absorption (`absorb3`, `absorbr3`), rotation (`rot3`,
  `align_lpow`) and TL use (`TLs` with an explicit result count) as an explicit rewrite.

**Main lemmas:**
- 7 generated crossing lemmas.
- `TL1` (one bounce) and `TLs` (TL iterated by induction).
- Families `PA`, `PB`, `PC`: the fixed point of the three rounds, found by `rounds.py`.
- The round lemmas `RA`, `RB`, `RC`, the endings `EA`, `EB`, `EC`, the y-ending `Y4` and `INIT`, all planner
  scripts (`rounds.py`, `endings.py`). Each is proved as `c -->+ ?c` followed by `?c = target`. That keeps the
  target out of the goal while stepping and speeds each step up about 15x.

**Hand-written tail** (`coq_tail.v.in`):
- clean arithmetic forms of the rules;
- `cycles` (n rounds of three) with bounds on `Nat.iter n G x`;
- `step_inv` for the invariant;
- `nonhalt` via `progress_nonhalt_cond`.

**Size:** about 18,000 literal steps are executed across all lemmas.

**Variants:**
- The same generator produced `BB8_48631_1RB0RD_D0_1RG.v`, run with `BB8TM` set to that variant.
- `variant3.py` generates `BB8_48631_1RB0RD_D0_0RH.v` and `BB8_48631_1RB0RD_D0_1RB.v`. It uses the same head,
  TL lemmas and planner, with the U1/U2 families, three rule lemmas, `INIT` and the tail `coq_tail3.v.in`.

**Compile times** (`check.py`, all PASS): main file 218 s, 1RG variant 222 s, 0RH and 1RB variants 21-23 s each.

## Notes and open questions

- **Growth signal:** the pipeline's rising digits per loop (1.23 -> 5.10) comes from QS's level-2 rule, which
  multiplies x by 27^3 per application, 10 applications per loop. It does not signal higher growth.
- **Known machines:** not compared against published BB(8) lists beyond our pre-filter.
- **Tooling:** `planner9.py` (affine counts, `kN` constants, evar targets, BFS normalization of run alignment)
  is reusable for other machines whose rules have large constants.
