## Configuration family and rules (verified)

Tape (head B on the blank right of everything, orientation R): `0^inf (10)^d1 0 (10)^d2 0 ... (10)^dn 0 (10)^a 0 (10)^(2b+1) 011 B>`.
Write W = [a, dn, ..., d1] (nearest the head first, an infinite run of zero digits at the far left) and F(W, b); the accumulator has b' = 2b+1 units, always odd, b >= 1.
A digit 0 is just one blank separator cell, so W has j "trailing zero digits" (zeros at the near end, counting a = 0); zeros at the far end merge into the blank.

| rule | condition (b >= 1) | F(W, b) -->+ | machine cost |
| --- | --- | --- | --- |
| R1 | W = (a+1) :: t | F(a :: t, b+1) | 12b + 54 |
| R2 (= R3A, j = 1) | W = 0 :: (y+1) :: t | F(2b :: y :: t, 1) | 36b + 102 |
| R3A | W = 0^j ++ (y+1) :: t, 1 <= j <= b | F(2^(j-1) ++ [2b-2j+2, y] ++ t, 1) | bilinear in (j, b) |
| R3B | j = b+1 | F(2^(b-1) ++ [y+3] ++ t, 1) | 12b^2 + 72b + 62 |
| R3C | j >= b+2 | F(2^b ++ 0^(j-b-2) ++ (y+1) :: t, 1) | same pass structure as R3B |
| R4 | W all zero (any j >= 0) | F(2^b, 1) | 12b^2 + 72b + 62 |

- The screen's fit "R3: 2b-2, tail=1, a = 2, b = 1" is the j = 2 (k = 1) instance. For k >= 2 zero digits the refill is 2b-2j+2 followed by j-1 twos (tail of 2s, not 1s), and the rule splits at j = b+1.
  The screen's "R4 KKKKK" is the list-exhausted rule R4: it writes exactly b digits "2" (b >= 1); there is no halting cell.
- Why there is no halt: R1 needs a positive nearest digit; otherwise the trailing zeros j and b >= 1 select exactly one of R3A, R3B, R3C (if the list has a nonzero digit) or R4 (if it is all zero); every result has b' = 1 or b+1 >= 1.
  The halting transition (state H reading 1, reached from D1 = `0LH` next to a 1) is never used by these rules.
- The note "b = 1 gives 0" is harmless: b = 1 (b' = 3): j = 1 is R2 (digit 2b = 2), j = 2 = b+1 is R3B, j >= 3 is R3C. b = 0 does not occur after the start.
- Dynamics: each digit decrement doubles b (b -> 2b+1 per full R1 run), R3A refills a digit of size about 2b followed by 2s, R4 rebuilds b twos: an Ackermann/tower-type counter that never reaches a halting cell.
- From the blank tape: first K event `F([1], 1)` at step 145 (K(;1;3)); R1 gives W=[0] (not parsed by the scan) then R4 gives `F([2,2], 1)` at step 465 (K((2);2;3)), then R1/R2/R3 as in `orbit1.py`.
  The Coq lemma `init` reaches `F [1] 1` in 145 steps.

## The precise remaining gap: machine-level lemmas R3Am, R3Bm, R3Cm (bilinear loops)

The statements are in the partial file (stream notation, `P = 1 1 0 0 1`, `[0;1;0;1]^^b`, `[0;0;1;0;1]^^k`, ...). What I learned about the process, for an Opus continuation:

1. **The autoproof engine cannot do R3 directly, and one of its loops is unsound.** Started on R3Am/R3Bm/R3Cm it finds a first "loop 1" that pairs each zero digit with one `(1010)` block and writes `(00101)^k`
   (after the D/H crossing of the b-run). `validate.reaches` shows that loop lemma is false for k >= 2 (true for one round): the round reads cells behind its insertion point, and in round 2 those cells hold the pushed blocks.
   The engine's `match_shift` check does not guard against that (Coq would reject the induction). Afterwards it runs into 441/2499-step literal segments (long alternating explicit cells that are really one run).
   Do not call `engine.explore` on the whole R3; give it waypoints.
2. **Real structure (read off concrete traces with `trace2.py` + `rle.py`):** after the D/H crossing the machine does j passes. The pass-start configuration is, in tape order,
   `X (10)^(y+1) 0^z 1 [E> (01)^(2c) 0 (01)^3 (10101)^d` (E reads the first cell of the run), pass i having z = j-i+1 zeros, c = b-i+1 and d = i-1 deposits.
   One pass: a loop crossing the run (20 steps per two units), a D/H crossing back, one zero turned into the marker `1`, two units of the run consumed, one `(10101)` deposited at the far end; cost about 24c + const, independent of d.
   After the last pass the left holds `(10)^y (01)^(2r+2)` and a transfer loop moves the d deposits one by one to the left as `0 0 1 0 1` blocks (41 steps each), then a few steps to the K shape
   (R3A, b = 6, j = 3, y+1 = 3: pass starts at steps 57, 216, 351; transfer 491 -> 630). R3B and R3C differ only in the last passes, where the run is exhausted (c = 1, 0).
3. **Proved piece (`Pass`, in the partial file):**
   `l (0)^z 0 0 0 1 E> (0101)^(c+2) 0 0 1 0 1 0 1 (10101)^d 0^inf  -->+  l (0)^z 0 0 1 E> (0101)^(c+1) 0 0 1 0 1 0 1 (10101)^(d+1) 0^inf` (stream form in the file; `passcfg.py`).
   It was found by `engine.explore` once the configuration was given as a waypoint (zeros as `z+3`, run as `c+2`). The lemma is false for fewer zeros or a shorter run: `pass2.py` shows it holds exactly for >= 3 zeros and >= 2 blocks (z in 0..2, c in 0..7, d in 0..5), cost 24*blocks + 15.
4. **Still to do** (each as a waypoint lemma: check with `validate.reaches`, then `engine.explore`, then `coqgen`, as for `Pass`):
   (a) Init: F-form start -> pass-1 start (z = j, c = b, d = 0): D/H crossing loop (`cr_HL_0101_0101`) then the C/A/B/D cycle;
   (b) iterate `Pass` (induction on the number of passes) while zeros >= 3 and run >= 2 blocks;
   (c) the special last passes (2 and 1 zeros, run of 1 and 0 blocks), which differ for R3A, R3B, R3C;
   (d) the transfer loop of the d deposits (41 steps each) and the final steps back to the K shape;
   (e) the same for the relative (`TM=... python gen_partial.py`; costs differ slightly, structure the same).
   The abstract side (F-form wrappers with `prog_eq`/`eq_norm`) is in place and the R3 lemma statements need not change.

How the three gaps were closed (generator `opus\gen891.py`, waypoints `opus\w891.py`, glue template `opus\r3glue.v.in`):
- Pass start, in stream form: PS(z, c, d) = left `1 0^z L`, head E, right `(0101)^c 0 (01)^3 (10101)^d`, where L = `1 (01)^y 0 t`
  (the digit y+1 without its first 0, so z counts every 0 up to the digit's first 1). `Pass` is PS(z, c, d) -> PS(z-1, c-1, d+1) for z >= 3, c >= 2.
- Each rule is: generated start segment (no loop) -> hand-written `PassIt` (induction on the number of passes) -> generated end segment.
  The end segment holds the last one or two passes and the transfer loop, and autoproof finds its loops by itself:
  - R3Am: start --R3A0--> PS(k+2, k+r+1, 0) --PassIt k--> PS(2, r+1, k) --R3A1--> target (r-loop across the run, then a k-loop moving the deposits);
  - R3Bm: start --R3B0--> PS(c+3, c+1, 0) --PassIt c--> PS(3, 1, c) --R3B1--> target;
  - R3Cm: start --R3C0--> PS(c+m+4, c+1, 0) --PassIt c--> PS(m+4, 1, c) --R3C1--> target.
  All six waypoints were first checked literally with `validate.reaches` (`opus\t2.py`, grids up to k, r, c <= 4, m <= 3, y <= 2), for both machines.
- Hand-written glue (`r3glue.v.in`): `zeros_shift`, `u2_double` (the R3A target writes the refill as `[0;1]^^(2 * r)`; R3A1 is generated
  against `0 0 1 0 1 [0;1;0;1]^^r`, and R3Am rewrites the target with `u2_double r`), `PassIt`, and the three chains. Every rewrite is fully instantiated.
- autoproof was **not changed**. The earlier "unsound loop 1" problem goes away with the waypoints, because the engine never sees the
