# BB(8) follow-up hunt — 2026-09-26

No new substantive BB(8) champion has been established so far. This note
records completed work and distinguishes finite search outcomes from proofs.

## Correction to the search strategy

The current BB(7) record was **found by enumeration**, not designed from a
known recurrence. The BBchallenge history identifies mxdys's C++ enumerator,
subtask 243308, Kropitz's discovery on May 10, 2025, and Ligocki's subsequent
analysis on May 13. The earlier README's suggestion that a new champion must
be hand-designed or take months to analyze was unjustified.

- History: https://wiki.bbchallenge.org/wiki/BB(7)
- Original enumerator: https://github.com/ccz181078/TM
- Analysis tools: https://github.com/sligocki/busy-beaver

The initial search in this folder rewards only machines that halt under a
small simulation budget. That is useful for finding modest finite records
but a poor discovery criterion for a machine whose huge behavior requires
recurrence proofs. The revised direction is broad tree-normal-form
enumeration, sound nonhalting filters, retention of difficult survivors,
and then stronger automatic or manual analysis. A cutoff remains unknown.

## Completed local searches and verification

- Independently reproduced the existing 131,112,087-step / 20,481-one local
  record using a literal JavaScript simulator (`audit_verification.json`).
- Proved all six distinct saved `run2_merged.json` holdouts nonhalting using
  an expanding-sweep invariant (`audit_notes.md`, `audit_unresolved.json`).
- Added neutral drift, occasional multiple-entry changes, per-worker seeded
  RNG, memoization, and reuse of the exact BB(5) prefix in `search3.py`.
  Compared its simulator against 1,000 random fixtures, including 380 literal
  halters and 292 snapshot/resume checks (`audit_search3.json`).
- Completed a four-worker, 180-second exploratory batch with 51,486
  evaluations (`run3_20260926.json`), with no new local record. This early
  batch used an insufficient deep budget for the existing record, so its
  negative result is weak. The script now has a 300,000-operation deep budget
  and a threshold based on steps since the saved prefix. The planned deeper
  rerun was interrupted before launch; no result is claimed for it.
- Exhaustively tested all 245 one-entry neighbors of the local record at
  positions E0/F0/F1/G0/G1/H0/H1 using 300,000 resumed operations: 59 halted,
  149 hit cutoff, 5 were proved infinite, and 32 had no halt transition.
  None of the observed halters improved the record (`audit_neighbors.json`).
  The top 12 cutoffs remained unresolved at macro block sizes 2, 3, and 4
  (`audit_neighbor_macros.json`).
- Tested 28 one-step BB(7) initializers and 1,303 split/start test cases
  covering 1,241 distinct labeled combinations. No stronger recognized B
  seed was found within the stated caps. These were narrow searches, not a
  general test of BB(8). See `theory_20260926.md`, `bb7_search_results.json`,
  and `bb7_search_initial_results.json`.

The BB(7) analysis page has small literal-configuration discrepancies under
our explicit halt-write/head convention, independently reproduced in
`audit_bb7_conventions.json`. These do not constitute a new machine or a
new championship claim; see the theory notes for the exact comparison.

## Discovery pipeline setup

`mxdys_main.cpp`, `mxdys_makefile`, and `mxdys_LICENSE` preserve the downloaded
public upstream source and license. `mxdys_pilot.cpp` is the local bounded
8-state adaptation; unprocessed frontier entries must remain separate from
the enumerator's holdouts, and timed-out tasks must never be called complete.

Ligocki source is pinned to commit
`1b31c66aece9d820fb937dcd51f82b02add581e8` under `third_party/ligocki`.
The downloaded tree manifest is `ligocki_tree.json`; Python dependencies are
isolated under `third_party/runtime_deps` (the first elevated installation
under `python_deps` is unused). SHA-256 hashes of the enumerator source and
binaries, plus measured run counts, are in `discovery_pilot_summary.json`.

These are incomplete slices, not completed shards, and nodes are partial
transition tables rather than a count of distinct complete machines.
Numeric shard identifiers do not describe identical regions for seven and
eight states. The short BB(7) shard run did not reach its champion.

A separate single-machine calibration did pass the actual BB(7) champion
through the entire original filter pipeline: it survived as a holdout in
0.095 seconds. An obvious loop was rejected and the BB(4) champion was
recognized as halting. See `mxdys_probe_calibration/`. This validates a key
regression condition without claiming a new proof of the BB(7) runtime.

Each of the 21 BB(8) holdouts has exactly one undefined transition. We
completed it with 1RZ and ran unmodified Ligocki Quick_Sim, first with a
10-second / 10,000-loop cap, then on the 17 remaining cutoffs with recursive
proofs and a 15-second / 100,000-loop cap. Automatic block selection was
used. No simulator errors were observed.

Final combined outcomes (`discovery_final.json`):

- Three halters: 2,002,855 steps / 1,862 ones; 871,820 / 271;
  and 21,136,127 / 6,846. All three were independently checked by literal
  JavaScript simulation (`audit_triage_halters.json`). None beats the
  existing 131,112,087-step local record, much less the BB(7) champion.
- Two machines classified nonhalting by the upstream automatic proof
  system. Their proof certificates were not independently audited here.
- Sixteen unresolved candidates, retained in `discovery_holdouts.txt`.
  Some accelerate to very large counts, but no halting conclusion follows
  from those counts. They are not established championship contenders.

The prover also reproduced BB(5)'s exact 47,176,870 steps and 4,098 ones in
334 simulator loops (`audit_ligocki_bb5.json`). Wrapper tests distinguish
halting, infinite, loop cutoff, wall timeout, and errors.

## Continuing the search

`mxdys_resume8.exe` resumes saved final-DFS frontier files without repeating
the completed prefix. It validates transition counts and preserves metadata.
Run from a fresh output directory with the compiler runtime on PATH, e.g.:

```powershell
$env:PATH = 'C:\msys64\ucrt64\bin;' + $env:PATH
$env:BB_PILOT_SECONDS = '175'
$env:BB_PILOT_PREFIX = 'next8'
& '..\mxdys_resume8.exe' resume '..\pilot8_243308\pilot8a_frontier.txt'
```

The interpreter used here is the bundled Python 3.12 executable reported by
workspace dependencies. With that interpreter:

```text
python ligocki_runner.py --input discovery_holdouts.txt --recursive --workers 2 --timeout 30 --max-loops 100000 --output next_triage.json
```

Results remain an exploratory search, not a BB(8) record. The important
change is that hard machines survive the discovery stage and are analyzed
afterward, rather than being discarded because direct simulation did not
reach a halt.
